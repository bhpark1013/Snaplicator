Snaplicator
Test DB for AI

Give your agent a database it is allowed to break.

Your agent cannot test a migration against seed data — the rows that break it only exist in production. It cannot test against production either. Snaplicator keeps one replica following your primary and hands out disposable copies of it: seconds to make, almost no disk, and nothing upstream notices when one is destroyed.

$ curl -fsSL https://raw.githubusercontent.com/bhpark1013/Snaplicator/main/deploy/install.sh | sudo bash

macOS: drop the sudo — it builds a Linux machine and continues inside it.

The loop

What an agent actually does with it

Agent

Takes a clone. Seconds, no coordination, nobody else affected.

Agent

Runs the migration. Drops the wrong column. Deletes without a WHERE.

Reset

Back to the snapshot it started from. The damage only ever existed in the clone's own blocks.

Agent

Tries the next version. The loop is seconds long, so being wrong is cheap.

It drives this itself. Snaplicator ships an MCP server, so creating, resetting and dropping clones are tools the agent calls — not steps you perform for it.

Why not the alternatives

A shared staging DB

One agent's failed migration is every other agent's flaky test. Parallel runs need isolation, and staging has none.

Restoring a dump

Correct, and an hour long. An agent's iteration is seconds; a reset that takes an hour is a reset it will avoid doing.

Seed fixtures

Fast and clean, and they never reproduce the bug. The row with the null you did not expect is in production, not in your factory.

Three words

Replica, snapshot, clone

Each is made from the one before it. That is the whole model — there is no fourth thing. Select a card to see what it costs you.

primary→ replica→ snapshot→ clone · clone · clone …

The part that makes it work

The pool is btrfs, so this is the filesystem's behaviour rather than a trick Snaplicator performs. Ten clones of a 300 GB replica are not 3 TB. They are 300 GB plus whatever the ten of them wrote.

Guide

From nothing to an agent with its own database

Steps 1–3 happen once. Steps 4–6 are the part your agent repeats.

1. Install 2. Choose tables 3. First copy 4. Snapshot 5. Clone 6. Wire up the agent

  1. Install and point it at the primary

    One line. It provisions the btrfs pool, starts the management plane and opens the UI. Answer the prompt with a connection URI — it only ever reads from that database — or with demo to seed a sample one first.

    # Linux
curl -fsSL https://raw.githubusercontent.com/bhpark1013/Snaplicator/main/deploy/install.sh | sudo bash

# macOS — no sudo; creates an OrbStack Linux machine and continues inside it
curl -fsSL https://raw.githubusercontent.com/bhpark1013/Snaplicator/main/deploy/install.sh | bash

  2. Choose what to replicate

    In the UI, with size and row count beside every table. Search narrows the list; the toolbar then sets everything matching in one go. Nothing is copied until you say so — a 300 GB decision should not be a default.

    Pick the tables your agent's work actually touches. A smaller selection means a faster first copy and smaller clones, and you can add more later.

  3. Run the first copy

    The schema is cloned, a subscription is created, and Postgres copies the selected tables in full. This is the one slow step and it happens once; the screen shows bytes landed against bytes expected. After it finishes the replica streams changes continuously, schema changes included.

  4. Take a snapshot

    A named instant of the replica, taken in O(1). This is what your agents will reset to, so take one when the data is in a state worth returning to — and take a fresh one whenever "current" has moved on.

    create_snapshot(name: "before-migration-42")
list_snapshots()

  5. Create a clone

    A writable Postgres on its own port, built from that snapshot. The reply carries the connection string; that string is the whole handoff to whatever runs the tests.

    create_clone(description: "agent-a / migration-42")
→ postgres://snaplicator:…@host:5455/appdb

    If the data is sensitive, configs/anonymize.sql runs while the clone is built — before anyone is given that string.

  6. Wire it into the agent

    Register the MCP server with your client and the loop becomes the agent's own. Scope which clones it may mutate with the clones query parameter — an accident guardrail, so a confused agent cannot reset one that is not its own.

    // .mcp.json
{
  "mcpServers": {
    "snaplicator": {
      "url": "http://snaplicator-host:8765/mcp?clones=5455"
    }
  }
}
    # the loop, in the agent's own words
create_clone(description: "try #1")   → port 5455
… run migration, run the suite, it fails …
reset_clone_to_snapshot(clone_id: "5455", snapshot_name: "before-migration-42")
… try #2 …
delete_clone(clone_id: "5455")
Keeping clones current

A clone is a fixed point — it does not follow the primary, which is exactly what makes a test repeatable. When you want newer data, take a newer snapshot and refresh_clone. The replacement is built beside the old one and swapped in only once it is serving, so clients see about half a second of unavailability rather than the whole rebuild.

Install

One line, then a UI

The installer surveys the host for somewhere to put the btrfs pool, provisions it, starts the management plane, and stops at the screen where you choose what to replicate.

Linux

$ curl -fsSL https://raw.githubusercontent.com/bhpark1013/Snaplicator/main/deploy/install.sh | sudo bash

Needs Docker. btrfs-progs, postgresql-client and the compose plugin are added if missing.

macOS

$ curl -fsSL https://raw.githubusercontent.com/bhpark1013/Snaplicator/main/deploy/install.sh | bash

btrfs is a Linux kernel filesystem, so there is nothing to install onto here. It creates an OrbStack machine named snaplicator and continues inside it.

No database to hand?

$ curl -fsSL …/install.sh | sudo bash -s -- --demo

Seeds a sample publisher so you can watch the whole thing work first.

Running it again

Re-running is how you upgrade: it refreshes the checkout and rebuilds. Nothing on the second run destroys anything — it offers to open what is already there, or to build a second install beside it with its own ports, pool and publication.
