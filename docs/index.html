Test DB for AI

Clone the production you already run, and test on that. No seeding, no dumps.

RDS, Azure Database for PostgreSQL, Cloud SQL or your own machine — production stays exactly where it is. Snaplicator keeps one replica following it and hands out clones that take seconds and almost no disk, and that your agent is free to break.

$ curl -fsSL https://raw.githubusercontent.com/bhpark1013/Snaplicator/main/deploy/install.sh | sudo bash

macOS: drop the sudo — it builds a Linux machine first.

The two things it does

Data and schema, replicated live

Logical replication carries rows and nothing else, which is why a copy of a managed primary normally has to be taken again on a schedule. Snaplicator catches CREATE, ALTER and DROP on the primary with event triggers and replays them here, so the replica never drifts out of shape.

Database branching

Freeze the replica into a snapshot, then start as many writable clones from it as you like. Seconds each, effectively no disk until something writes, and putting one back is a single call.

Is this you?

Use it if

  • Production is on RDS, Azure Database for PostgreSQL, Cloud SQL or a machine you own, and you are not moving it.
  • You need real production data to test against, and it cannot leave your own infrastructure.
  • You run several agents at once and each needs a database it is free to destroy.
  • Your schema changes often enough that taking the copy again on a schedule has become a chore.

Look elsewhere if

  • You cannot set wal_level=logical or create a replication slot on the primary. Stop here — nothing else works without it.
  • You already run on Neon or Supabase. Use their branching; a branch there is your data.
  • You need high availability. One machine, one pool, no failover — losing the replica costs you clones.
  • You are looking for a production database. This is a test copy, not somewhere to serve from.

What an agent actually does with it

Agent

Takes a clone. Seconds, and nobody else is affected.

Agent

Runs the migration. Drops the wrong column. Deletes without a WHERE.

Reset

Back to the snapshot it started from. The damage never left the clone.

Agent

Tries the next version. Being wrong costs seconds.

Snaplicator ships an MCP server, so the agent calls all of this itself. You are not in the loop.

When you reach for it

A bug in production, right now
The row that causes it only exists in production. Take a snapshot, make a clone, and seconds later you are querying the same data — on a copy you are free to break while the incident is still open.
A migration you don’t trust
It passed against seed data because seed data has none of the nulls, duplicates and orphaned rows that production accumulates. Run it on a clone; if it breaks, reset and try the next version.
Several agents at once
Each gets its own clone on its own port. One of them dropping a table is not the other one’s flaky test.
A query plan you can believe
Same size, same statistics, same indexes as production. A plan that is instant over a small staging table is not instant over the real one.

Why not the alternatives

A shared staging DB
One agent’s failed migration is every other agent’s flaky test.
Restoring a dump
Correct, and it scales with the size of the database. A reset the agent waits on is a reset it works around.
Seed fixtures
Fast, clean, and they never reproduce the bug. The unexpected null is in production, not your factory.

How this compares to Neon, Aurora and DBLab

All of these do copy-on-write. What differs is where your data has to live for it to work.

  Runs where A copy starts with How it stays current Schema changes
Neon Neon’s cloud the parent branch, instantly it is your database — branches are of the real thing come with the branch — same storage
Supabase Supabase’s cloud nothing — no production data at all you seed it yourself applied from your migration files
Aurora cloning AWS, Aurora only the source cluster’s pages clone again for fresher data come with the clone — same storage
DBLab your hardware, any Postgres the last retrieved copy self-managed: continuous. Managed (RDS): periodic full refresh physical: with the copy. Managed: only at the next full refresh
Snaplicator your hardware, any Postgres the snapshot you picked logical replication, continuously — managed primaries included captured on the primary and replayed here, continuously

The schema column is the interesting one

Postgres is blunt about this: The database schema and DDL commands are not replicated. That is why following a managed primary usually means re-copying it on a schedule — the alternative is a replica whose schema drifts until replication errors out.

Snaplicator captures DDL on the primary with event triggers, ships it through the same publication, and replays it on the replica. Add a column at 14:02 and the replica has it at 14:02 — no refresh, no re-dump.

Production is on Aurora. Something is wrong with the data, and it is wrong now.

With a copy that refreshes on a schedule

Your copy is as old as the last refresh. To reproduce what is happening you start a full dump and restore, and then you wait — while the incident continues. If a migration shipped this morning, the schema is wrong too.

With a replica that never stopped following

Already current — rows and schema both. Take a snapshot, make a clone, and you are querying production-shaped data from moments ago. Nothing you waited for was a dump.

Where the differences actually bite

Neon and Supabase branching
Both are excellent, and if you already run on them, use their branching — a branch there is your data. Neon will also follow an RDS or Cloud SQL primary over logical replication rather than hosting it, and then two things change: the data lands in Neon’s cloud, and the schema becomes yours to keep in step — their guide requires that the tables in the source database you are replicating from must also exist in the destination database, and they must have the same table names and columns. That is the gap the next section is about.
Aurora fast cloning
Copy-on-write at the storage layer, and genuinely fast — but a clone is a DB cluster, and a cluster needs an instance, so every clone bills compute. AWS also caps it: You can create up to 15 clones with copy-on-write protocol. After you have 15 clones, the next clone that you create is a full copy. Aurora only, not plain RDS Postgres.
DBLab (Postgres.ai)
The closest thing to this, older and more capable — it will clone 10 TiB in under two seconds. The difference is how the copy keeps up. Its physical mode is not available for managed cloud Postgres services such as Amazon RDS; against those it is dump/restore on a schedule. Snaplicator subscribes over logical replication, so a managed primary is followed rather than re-copied.
If you run on Supabase

Branches there start with no production data by design, and Supabase can act as a logical-replication publisher — wal_level is already logical. Two caveats from their own guide: use the direct connection string rather than the pooler, and the subscriber needs IPv6 or their IPv4 add-on.

The part that makes it work

The pool is btrfs, so this is the filesystem’s behaviour, not a trick. Ten clones of a 300 GB replica are 300 GB plus whatever the ten of them wrote.

From nothing to an agent with its own database

  1. Install and point it at the primary

    It provisions the btrfs pool, starts the management plane and opens the UI. Answer the prompt with a connection URI — it only ever reads — or demo for a sample database.

    # Linux
curl -fsSL https://raw.githubusercontent.com/bhpark1013/Snaplicator/main/deploy/install.sh | sudo bash

# macOS — no sudo; creates an OrbStack Linux machine and continues inside it
curl -fsSL https://raw.githubusercontent.com/bhpark1013/Snaplicator/main/deploy/install.sh | bash

  2. Choose tables, then run the first copy

    In the UI, with size and row count beside every table. Nothing is copied until you say so — pick what your agent actually touches, and add more later.

    The schema is cloned, a subscription is created, and Postgres copies those tables. This is the one slow step and it happens once. After it, the replica streams changes continuously.

  3. Decide what gets scrubbed

    Copy the example to configs/anonymize.sql, or edit it from the UI. It runs inside every clone built from the live replica, before the port is handed out.

    cp configs/anonymize-example.sql configs/anonymize.sql

UPDATE user_account SET email = 'dev+' || id || '@example.local';
UPDATE device_info  SET push_token = 'invalid-dev-token', is_push_enabled = false;

    If the script fails, the clone is destroyed rather than served — a half-scrubbed copy is never handed to anyone. A clone with no script at all is production data given to whoever asked for it, so the file’s absence is reported, not assumed.

  4. Let the schema follow too

    Logical replication carries rows only. Snaplicator puts event triggers on the primary that write every CREATE, ALTER and DROP into an outbox table — and that table is itself in the publication, so the DDL arrives as ordinary replicated rows and is replayed here.

    install_trigger()
get_trigger_status()

    A table created on the primary is added to the publication automatically, so it starts replicating without you touching anything. Capture is deliberately wide; what to skip is decided when it is replayed.

  5. Everything above happens once. Everything below, the agent repeats on its own.

  6. Take a snapshot

    A named instant of the replica, taken in O(1). This is what your agents reset to, so take a fresh one whenever ‘current’ has moved on.

    create_snapshot(name: "before-migration-42")
list_snapshots()

  7. Create a clone

    A writable Postgres on its own port, built from that snapshot. The reply carries the connection string — that string is the whole handoff.

    create_clone(description: "agent-a / migration-42")
→ postgres://snaplicator:…@host:5455/appdb

  8. Wire it into the agent

    Register the MCP server and the loop becomes the agent’s own. The clones query parameter scopes which clones it may touch, so a confused agent cannot reset someone else’s.

    // .mcp.json
{
  "mcpServers": {
    "snaplicator": {
      "url": "http://snaplicator-host:8765/mcp?clones=5455"
    }
  }
}
    # the loop, in the agent's own words
create_clone(description: "try #1")   → port 5455
… run migration, run the suite, it fails …
reset_clone_to_snapshot(clone_id: "5455", snapshot_name: "before-migration-42")
… try #2 …
delete_clone(clone_id: "5455")
Keeping clones current

A clone is a fixed point — that is what makes a test repeatable. For newer data, take a newer snapshot and refresh_clone. The replacement is built beside the old one and swapped in once it is serving, so clients see about half a second.

Where it can go sideways

A clone made from a snapshot is not anonymized
The script runs only on clones spawned from the live replica. One taken from an existing snapshot skips it — scrub that clone yourself before it leaves your hands.
CREATE INDEX CONCURRENTLY
It cannot run inside the apply worker’s transaction, so it is queued to _snaplicator_ddl_deferred and run outside it rather than failing.
A DDL statement that fails here
It is written to _snaplicator_ddl_failures and left there — not retried, not patched over. A schema you can see is wrong beats one that looks right and is not.
Schema changes made before you installed
A watermark stops anything older than the trigger install from being replayed. The schema is cloned once at setup and the triggers take it from there.
Knowing it is actually keeping up
configs/replication_check.sql runs on both the primary and the replica and the two results are compared. It is forced read-only: writes and DDL are rejected on save, and it executes inside a READ ONLY transaction.
